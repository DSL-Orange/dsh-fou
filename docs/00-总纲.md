## 零、一句话

> **协议是「我们承诺给别人什么」；代码是「我们现在做到什么」。**
> **先写协议 = 先承诺，再兑现。**

## 一、为什么单独立项（不塞进 40-项目）

| | 项目文档 | **协议** |
|---|---|---|
| 生命周期 | **只追加**（历史） | **覆盖**（当前有效） |
| 读者 | 我们自己 | **所有会话**（百科 / 地颂 / 机师 / 未来的插件作者） |
| 错了怎么办 | 不改写，追加修正 | **直接改，记一笔变更** |
| 类型 | 报告 / 日志 | **快照**（必须写 `水位：`） |

**"水位"是什么**：**这份记录最新有效到哪一天**。`records-check.mjs` 会查它 ——
**过期就有人来问"还作数吗"**，而不是半年后所有人还在按一份老协议干活。

## 三、总纲要回答的四件事

### ① 有哪些协议、各自管什么

**见 §二 目录。** 每条协议开头必须有一句"**这条管什么、不管什么**"。

### ② 每条协议"谁读它"

**同一份协议，Agent 读法和人读法不同** —— 所以每条协议开头要标读者：

| 读者 | 要回答的问题 |
|---|---|
| **会话 / Agent** | 我怎么接入？调什么？拿到什么？ |
| **人** | 它现在能干什么？怎么用？坏了我怎么知道坏了？ |
| **未来的插件作者** | 我写的插件能不能用？要遵守什么？ |

**（当前只有一个"人"—— 所以人那节可以先薄，但结构要留。）**

### ③ 怎么加一条新协议

**三条门槛，缺一不立**：

1. **有人要用**（至少一个会话/插件需要它，不是"以后可能"）
2. **它是"契约"而不是"实现说明"**（写"我会给你什么"，不写"我内部怎么实现"）
3. **它能被验证**（有明确的"做到/没做到"判据）

**加之前先看**：**能不能并进已有子协议** —— 协议越少越好，**因为协议是别人的负担**。

### ④ 协议与代码，谁先

> **协议先行。**（2026-11-06 起，贯彻"记录 > 规划 > 执行"）

**理由**：**代码是"现在做到什么"，协议是"我们承诺给别人什么"。**
**先写协议 = 先承诺，再兑现。**

**历史反例**：2026-11-05 深夜那次崩溃，我们一直是"先做、再回头总结" ——
**所以承诺从来没写下来，也就没有人能替我们检查。**

## 四、变更纪律

| 动作 | 怎么做 |
|---|---|
| **改一条协议** | 直接改本条（**覆盖**），水位更新到当天，并在 `_变更.md` 记一行 |
| **新增一条协议** | 过 §三③ 三道门槛；总纲 §二 目录加一行 |
| **废弃一条协议** | **不删**，标 `⛔ 已废弃（日期 / 原因 / 替代者）` |
| **协议与代码不一致时** | **以协议为准**，代码要么改，要么改协议（二选一，不许放著） |
