## 一、浮游插件区 = 界面划分，不是方式划分（用户 2026-11-08）

> **"浮游插件 区域 是一个 界面划分，而不是 方式的划分。"**

**意思是：那个区域里可以有多种"打开方式"，区域本身不规定必须怎么打开。**

```
浮游插件（一个【区域】）
  ├─ 打开方式 ① 硬挂载 mount      → 内容型、无页面（速写）          ✅ 已通
  ├─ 打开方式 ② 在浮游中打开 URL  → 有页面的插件 / 外部服务        ✅ 已通
  └─ 打开方式 ③ 遥控 run          → 窗口型（地颂）                  ✅ 已通
```

**推论**：
- **协议规定的是"打开方式有哪几种、各自要什么"，不是"插件区该放什么"。**
- **区域是界面的事，方式是协议的事。两者不该混。**
- 例：像「上下文洞察」那种能做到四形态的插件，**可以按"在浮游中打开"的方式进来，只是形式上放在插件区**。

## 二、唯一的入口

```js
window.__fouDock.register({ id, label, icon?, run, kind? })
// 返回 true / false；false 只表示"现在不行"，永远不是错误
```

**软依赖铁律**：

> **浮游不在时，插件必须完全照常工作。** —— **不许 import 浮游的任何东西，不许打日志。**

## 三、两条路（2026-11-08「硬挂载」）

```js
__fouDock.register({ id, label, icon?, run?, mount?, kind? })
```

| 字段 | 类型 | 含义 | 点它 → |
|---|---|---|---|
| **run** | 动作 | **软挂靠**：发生一件事（遥控 / 自己弹窗） | 调 run() |
| **mount** | 函数 | **硬挂载**：`(container) => cleanup`，把界面画进浮游给的容器 | **挂进开间（活的）** |

**硬挂载的接口约定（浮游侧已实现 2026-11-08）**：

```js
mount(container) {
  // container 是一个 **Shadow Root**（空的）
  // 插件往里画自己的界面；样式自然隔离（shadow 里的出不来，外面的进不去）
  const root = ReactDOM.createRoot(container)   // 或纯 DOM 也行
  root.render(<YourUI />)
  return () => root.unmount()                    // 必须返回 cleanup
}
```

**三条保证与分工**：

| # | 浮游保证 | 插件负责 |
|---|---|---|
| 1 | **有一个空盒子**（Shadow Root） | 往盒子里画什么 |
| 2 | **隔离**（shadow DOM + 外层错误边界） | **好看**（样式、布局、留白） |
| 3 | **清理**（卸载时调 cleanup，再清空 shadow） | cleanup 真的把定时器/监听器收掉 |

> # **[浮游，插件]：[硬挂载，软优化]**
> **能用，浮游保证；好看，插件自负。**

**推论**：**崩了/挂不上 → 浮游；丑了/挤了 → 插件。**

### 选哪条路：看插件形态（2026-11-08 实测得出）

| 插件形态 | 特征 | 该用哪条 | 实证 |
|---|---|---|---|
| **窗口型** | 自己是浮窗 / 有 `position:fixed` / 有球·胶囊多态 | **软挂靠（run）** | **地颂**：硬挂载后跑到右下角 + 出现两个实例 |
| **内容型** | 面板 / 列表 / 编辑器，流式布局，只在侧栏或主区 | **硬挂载（mount）** | **速写**：挂进开间自然铺开，功能全通（2026-11-08 14:43） |

> # **窗口型 → 软挂靠；内容型 → 硬挂载。**
> **判据的实质：一个「已经有自己的窗口」的插件，再给它一个容器，就等于给它两个身体。**

**为什么速写是理想的第一位客人**：
1. **没有浮窗形态**（只在侧栏）→ 不会出现两个实例
2. **流式布局** → 挂进容器自然适应，不需要改 UI
3. **只依赖 `props.t`** → 挂载只需 40 行（纯新增，一行 UI 不动）

**「改动小到对方看了不会反对」（用户 2026-11-08）**：
> **这是「先建后批」能成立的前提 —— 只动协议侧，不动本体侧。**
> **如果我们改得对方认不出自己的插件，那就不是「先建后批」，是「先斩后奏」。**

### 判据的实证（2026-11-08 22:07 验收通过）

| # | 插件 | 形态 | 方式 | 结果 |
|---|---|---|---|---|
| 1 | **地颂** | **浮窗** | **遥控（播放/暂停）** | ✅ 点它就播/停，两边都不弹窗 |
| 2 | **速写** | 侧栏 | 挂载 | ✅ 写稿保存通畅 |
| 3 | **市场** | 侧栏 | 挂载 | ✅ **活界面** —— 用户在开间里装了壁纸插件 |
| 4 | **百科** | 侧栏 | 挂载 | ✅ 74 条，能搜能读 |
| — | 观测 | 侧栏 | 挂载（代码已写） | ⏸ **插件未安装，未验** |

> # **四发四中：侧栏插件→挂载 / 浮窗插件→遥控。**

**"活界面"这条证据最关键**：用户在开间里的市场**装了插件** —— 证明挂进去的不是快照，是**能办事的界面**。

## 四、最小字段（当前已实现）

| 字段 | 必填 | 说明 |
|---|---|---|
| `id` | ✅ | 全局唯一。同 id 再注册 = **覆盖**（HMR 重挂无害） |
| `label` | ✅ | 显示名（走插件自己的词典） |
| `icon` | 🟡 | 一个字符（`♫` / `∼`） |
| `run` | ✅ | **点击后干什么**。**注意：它只是"一个动作"，不是"打开浮游"** |
| `mount` | 🟡 | **硬挂载**：收到一个空 Shadow Root，往里画界面，返回 cleanup（见 §三） |
| **`brief`** | 🟡 | **简讯**（2026-11-09 新增）：返回 `{ icon, text }` 或 `null`，让浮游的胶囊左栏能把"应用槽位"切到你 |

### `brief` 契约（2026-11-09 实测通过）

**它的作用**：让插件能把**一条当前状态**报给浮游，浮游胶囊的**左栏应用槽位**就能切到它。

```js
brief: () => ({ icon: '▶', text: '河北墨麒麟' })   // 有状态
brief: () => null                                   // 此刻没什么可报 → 浮游干净回退
```

| 规则 | 说明 |
|---|---|
| **同步、快、无副作用** | 浮游每 2 秒调一次（停在你的应用上时） |
| **没状态就返回 `null`** | **别返回 `{ text: '' }`** —— 那会让浮游显示一个空白胶囊 |
| **`icon` 可省** | 省了就用你注册时的 `icon` |
| **`text` 是一行** | **别塞多行，也别塞长段落** —— 它在 44px 高的胶囊里 |
| **没有 `brief` 的插件不参与切换** | 因为"没有当前状态"的插件，点了会切到空白 |

**⚠ 应用槽位怎么切：点左栏轮转，不用滚轮。**
**因为滚轮已经归"胶囊三态"了 —— 一个输入通道只干一件事（2026-11-09 敲定）。**

**参考实现**：地颂（`song.dock`）—— `brief()` 返回"播放中/暂停 + 歌名"，
`run` 同时是**播放/暂停**，所以浮游胶囊切到它时：**左栏 `♫`、右栏歌名、点胶囊 = 播放/暂停**。

## 五、`kind` —— 区分"谁注册的"（2026-11-08 新增，待实现）

**问题**：浮游自己的坞自检（`fou.hop`）和地颂的播放器（`song.dock`）**走的是同一个入口**，
所以坞里分不清"这是插件还是宿主自己的东西"。

**而这正是它健康的地方**：

> # **一个 API 如果连它自己的作者都不走，那它一定有毛病。**

**所以 `kind` 不是为了隔离，是为了"如实标注"**：

```js
__fouDock.register({ id, label, icon, run, kind: 'plugin' | 'self' })
```

| `kind` | 谁用 | 菜单里的归处 |
|---|---|---|
| `'plugin'`（缺省） | 外部插件 | **挂靠** |
| `'self'` | 浮游自己的功能（自检等） | **设置** |

**在 `kind` 落地之前**，浮游靠 id 前缀临时判断（如 `fou.hop` 归设置）。

## 六、宿主重载后的重连（2026-11-08 新增，**已实测并修复**）

### 问题

**宿主（浮游）热重载会生成一个全新的 `window.__fouDock`**，
而插件的注册通常只在挂载时做一次 → **旧坞里的条目随旧坞作废，新坞里是空的**。

**用户 2026-11-08 实测**：浮游在插件页 关 → 开 之后，**地颂从挂靠区消失**。

### 契约（插件侧的责任）

> **插件必须自己检测"我注册的那个坞还在不在"，不在就重注册。**
> **宿主不负责替插件兜底** —— 因为宿主也不知道有哪些插件。

### 参考实现（地颂 v1.7.0 → 2026-11-08 改）

```js
const registeredDockRef = { current: null };

function registerDock(label) {
  const dock = readDock();
  if (!dock) return false;
  const ok = dock.register({ id, label, icon, run });
  if (ok !== false) registeredDockRef.current = dock;   // 记住"注册到哪个坞"
  return ok !== false;
}

// 每 3 秒对照一次：坞换了 → 重注册
window.setInterval(() => {
  const dock = readDock();
  if (!dock) return;
  if (dock === registeredDockRef.current) return;   // 同一个坞，不折腾
  registerDock(label);
}, 3000);
```

**为什么是"对照实例"而不是"定时重注册"**：
**定时重注册会覆盖同 id 的条目**（虽然无害，但会有一次多余的写）**；对照实例只在真的换了时才动。**

**用户 2026-11-08 实测结果**：**未重载即生效**（改 client.js 触发 HMR → 新代码上场 → 3 秒内重连成功）。

## 九、未来方向：**浮游主动扫描**（用户 2026-11-08 提出）

> **"浮游主动注册插件，就像一个 UFO，把插件扫一遍，加进来。"**

**判断：分两层，别混。**

| 层 | 是什么 | 能否不靠插件配合 |
|---|---|---|
| **① 发现** | 浮游知道"装了哪些插件" | ✅ **能** —— 宿主半可读 profile 的 bundles |
| **② 挂靠** | 浮游把某个插件**打开**在开间里 | ❌ **不能** —— 必须知道"怎么打开它" |

**难点在②**：官方插件页面走的是 `dsh-app://` 内部路由（不是 http），
**浮游的 iframe 打不开**（不同源）。

**所以"UFO 扫描"的正确形态是**：

| 模式 | 谁做什么 |
|---|---|
| **扫描（浮游主动）** | 列出"你装了但没挂靠"的插件 → 像"附近的人" |
| **挂靠（插件配合）** | 插件提供一句 `register()` 或一个可打开地址 |
| **半自动（折中）** | 扫描发现 → 浮游问"这个能挂吗" → 用户点一下 → 试打开 |

> **扫描解决"我不知道有你"；协议解决"我不知道怎么用你"。**

**而扫描的真实价值不在"自动全挂"（做不到），在"让你看见还没用上的东西"。**
